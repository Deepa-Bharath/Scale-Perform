Purpose
This document captures the AWS resources we created for deploying the Scale-Perform service, why each one is needed, what was confirmed during setup, and what is still left before the API can be accessed through AWS.

Current target architecture
Internet -> Application Load Balancer -> ECS service on EC2 -> Node.js app
                                                      -> MongoDB
                                                      -> Redis (private IP when used)

Chosen AWS environment
- Region: ap-south-1 (Mumbai)
- VPC: vpc-0f219df35ad6b17c1
- Subnet 1: subnet-09b3b11e1c1b9d879
- Subnet 2: subnet-0f89883a3ed91fdd3
- Redis private IP: 172.31.32.246

Why VPC and subnets are needed
- The VPC is the private AWS network where ECS, ALB, and backend services communicate.
- The subnets are where the load balancer and ECS container hosts are placed.
- Two subnets in different Availability Zones are preferred so the ALB can span multiple AZs.
- Redis can be reached privately inside the VPC instead of being exposed publicly.

Step 6: Create the ECS cluster and EC2 capacity
What we did
- Created the ECS cluster:
  scale-perform-cluster
- Used ECS on EC2, not Fargate.
- An EC2 instance was launched as the ECS container host.
- A capacity provider backed by an Auto Scaling group was auto-created by the ECS flow.

Why needed
- The ECS cluster is the control plane where services and tasks will run.
- The EC2 instance is the machine that will host the application containers.
- The capacity provider connects ECS task scheduling to the EC2 Auto Scaling group.

Important lesson from the session
- Stopping the EC2 instance directly is not the right way to pause costs when it belongs to the Auto Scaling group.
- The Auto Scaling group will recreate or bring back capacity if desired capacity is still above zero.

Status
- Confirmed created and running.

Step 7: Security groups, target group, and ALB
Security groups created
- scale-perform-alb-sg
- scale-perform-app-sg

Why they are needed
- scale-perform-alb-sg:
  Allows inbound HTTP 80 from the internet to the ALB.
- scale-perform-app-sg:
  Allows inbound app traffic on port 5000 only from the ALB security group.

Target group created
- scale-perform-api-tg

Why target group is needed
- The ALB does not send traffic directly to the ECS service.
- It forwards to a target group.
- ECS later registers and deregisters task IPs in this target group.
- Health checks such as /health are defined on the target group.

ALB created
- scale-perform-alb

Why ALB is needed
- Provides a public entry point for the application.
- Distributes traffic across healthy ECS tasks.
- Makes service scaling and health checks practical.

Important networking note
- The EC2 host can still have a public IP.
- ALB to target communication still uses private IPs inside the VPC.
- Redis should be reached over private IP only.

Status
- Target group confirmed created.
- ALB confirmed created.

Step 8: Create the ECS task definition
Task definition created
- Family: scale-perform-api

Why needed
- A task definition is the blueprint for the app container:
  image, port mappings, roles, logs, env vars, and resource requests.

Important lesson from the session
- The EC2 host can exist before the task definition exists.
- The host is only compute capacity.
- The task definition tells ECS what container to run on that capacity.

Resource sizing lesson
- The EC2 host is a t3.micro.
- Task CPU and memory values must fit on that host.
- Large defaults like 1 vCPU and 3 GB are not practical on a 1 GiB host.

Cost and shutdown lessons
Why the EC2 instance came back after being stopped
- The ECS cluster is backed by an Auto Scaling group through the capacity provider.
- If desired capacity is still above zero, Auto Scaling recreates or restarts capacity.

Correct low-cost park mode for this setup
- Set ECS service desired count to 0.
- If service autoscaling is enabled, set min tasks to 0 or disable it.
- Set the Auto Scaling group desired capacity to 0.
- Set the Auto Scaling group min capacity to 0.
- Delete the ALB if minimizing cost aggressively, because ALB is billed while it exists.
- Stop standalone Redis or Mongo EC2 instances if they are not part of Auto Scaling.

What can usually remain without major runtime cost
- VPC, subnets, route tables
- Security groups
- IAM roles
- ECS cluster metadata
- ECS task definitions
- SSM parameters
- ECR repository shell

Important cost notes
- ECS on EC2 does not add an extra ECS charge by itself, but EC2, EBS, ALB, and public IPv4 can still cost money.
- ALB is not free to keep around continuously.
- Public IPv4 usage can also incur cost.
- NAT gateways should be avoided for this learning setup unless truly needed, because they add hourly cost.

Learning-mode summary
- Goal:
  Experience a realistic architecture with ALB, ECS on EC2, health checks, and scaling.
- Tradeoff:
  Better learning realism than a single EC2 instance, but more moving parts and more billing risk.
- Cost discipline:
  Keep desired task count low, avoid unused ALBs or NAT gateways, and scale ASG and ECS service to zero when parked.
